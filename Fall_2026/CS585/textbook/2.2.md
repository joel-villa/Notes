## 2.2.1 Overview of HTTP

- *HyperText Transfer Protocl* (HTTP): "the Web’s application-layer 
  protocol", HTTP defines message structure and exchange
- Two implementations, executed on seperate end systems:
    - Client
    - Server
- *Web Page*: 
    - base HTML file + several referenced objects (most of the time)
    > "The base HTML file references the other objects in the page with the objects’ URLs"
- *Object*: a file
- URL's two components:
    1. Object's Server's hostname
    2. Object's path name
> "HTTP uses TCP as its underlying transport protocol"
-  *Stateless Protocol*: server stores no information about the clients
    - HTTP is stateless

## 2.2.2 Non-Persistent and Persistent Connections

- *Non-Persistent Connections*: request/response pairs sent over a seperate 
  TCP connection
- *Persistent Connections*: request/response pairs sent over the same TCP 
  connection
- HTTP by default is persistent, but it can be configured to be non-persistent

### HTTP with Non-Persisten Connections

- EXAMPLE: File transfer of a base HTML file 
  (http://www.someSchool.edu/someDepartment/home.index) + 10 JPEGs:
    1. HTTP client initiates TCP connection to oserver www.someSchool.edu, on 
       port 80 (default for HTTP). There will be a socket at client and server 
       associated with th econnection
    2. HTTP client sends HTTP request to server via socket, request message 
       includes path name '/someDepartment/home.index'
    3. HTTP server receives request from socket, retrieves object, encapslates 
       object in an HTTP response message, sends the message to the client via 
       its socket
    4. HTTP server process closes the TCP connection (TCP doesn't terminate 
       until the client has recieved the message)
    5. HTTP client receives response message, TCP connectio terminates, 
       message indicates the encapsulated object is an HTML file, client 
       extracts files
    6. First four steps are repeated for each of the referenced JPEG objects
> "The HTTP specifications ([RFC 1945] and [RFC 7540]) define only the communication protocol between the client HTTP program and the server HTTP program"
> "Browsers may open multiple TCP connections and request different parts of the Web page over the multiple connections"
- *Round-Trip Time* (RTT): "amount of time that elapses from when a client 
  requests the base HTML file until the entire file is received by the client"
- "Back-of-the-envelope calculation for the time needed to request and receive 
  an HTML file" (three-way handshake):
    - The first two parts take one RTT: "the client sends a small TCP segment 
      to the server, the server acknowledges and responds with a small TCP 
      segment, and finally, the client acknowledges back to the server"
    - Now client sends request, waits another RTT + transmission time of file 
      until they have all of the message
    - Total time: "two RTTs plus the transmission time at the server of the 
      HTML file"
- CONS:
    - Each requested object = new connection to establish + maintain
    - New connection = new TCP buffers + variables kept in both client and 
      server
      
### HTTP With Persistent Connections

- PROS:
    - "requests for objects can be made back-to-back, without waiting for 
      replies to pending requests (pipelining)"

## 2.2.3 HTTP Message Format

```
GET /somedir/page.html HTTP/1.1
Host: www.someschool.edu
Connection: close
User-agent: Mozilla/5.0
Accept-language: fr
```

- Request Message:
    - *Request line*: "first line of an HTTP request message"
        - 3 fields:
            1. Method Field
                - `GET`: browser requests
                - `POST`
                - `HEAD`
                - `PUT`
                - `DELETE`
            2. the URL field
            3. HTTP version field
    - *Header Lines*: "lines that follow the request line"
        - Examples:
            - Host
            - `Connection: close` -> non-persistent connection
            - User-agent: the browser type (ex Moozilla)
            - Accept-language: indicates preferred language
- A request generated with a form does not have to use the `POST` method:
    - The HTML form can use `GET` and include input data in the requested URL

### HTTP Response Message

- EX:
```
HTTP/1.1 200 OK
Connection: close
Date: Tue, 18 Aug 2015 15:44:04 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Tue, 18 Aug 2015 15:11:03 GMT
Content-Length: 6821
Content-Type: text/html
(data data data data data ...)
```
- Three Sections:
    1. *Status Line*: protocol version filed, status code filed, corresponding 
       status message field
        - Common status codes:
            - `200 OK`: request succeeded
            - `301 Moved permanently`: the new URL is specified in `Location:`
              header
            - `400 Bad Request:` generic error
            - `404 Not Found:` document DNE
            - `505 HTTP Version Not Supported:`
    2. *Header Lines*
        - `Connection: close`: notify client that the TCP connection will be 
          closed
        - `Date:` indicates time and date of server retrievign object 
        - `Server:` what server?
        - `Last-Modified:` wehn was the object last modified
        - `Content-Type:` indicates type of the entity body
    3. *Entity Body*: meat, contains requested object
- Which header lines?
    > "There are different products, versions, and configurations, all of which influence which header lines are included in response messages."

## 2.2.4 User-Server Interaction: Cookies

- Four Components:
    1. Header in HTTP response message
    2. Header in HTTP request message
    3. Cookie file kept on user's end system
    4. back-end database at the Web site
> "Although the Amazon Web site does not necessarily know Susan’s name, it knows exactly which pages user 1678 visited, in which order, and at what times"
- Cookies are used to "create a user session layer on top of stateless HTTP"
- "using a combination of cookies and user-supplied account information, a Web site can learn a lot about a user and potentially sell this information to a third party"

## 2.2.5 Web Caching

- *Web Cache* (proxy server): "network entity that satisfies HTTP requests on 
  the behalf of an origin Web server"
- Web cache's are both clients and servers
- Without a web cache, total response time is sum of LAN delay, access delay, 
  and Internet delay

### The Conditional `GET`

- *Conditional GET*: a mechanism that allows a cache to verify that its 
  objects are up to date
- NOTE: this has an empty body (fast) if the cache is up to date, and adds
  little overhead if cache is not up-to-date

## 2.2.6 HTTP/2

-  Primary goals of HTTP/2:
    - Enable request and response multiplexing over a single TCP -> reduced 
      perceived latency
    - Provide request prioritization and server push
    - Efficient HTTP compression
    - **Get rid of parallel connections for transporting a single Web page**:
        - Occurs due to HOL blocking + TCP congestion control (a workaround is
          using multiple connections to increase bandwidth)
- *Head of Line (HOL) blocking*: web page sends big video, then smaller images,
  the smaller images get blocked by the big boy

### HTTP/2 Framing

- HOL blocking solution: break message into small frames
- Frame interleaving: send frames from various resources in a round robin style
- Framing sublayer also binary encodes the frames => more efficient parsing, 
  smaller frames, less errors

### Response Message Prioritization and Server Pushing

- Message prioritization => devs can customize priority of requests to 
  optimize app performance
- Server pushing:
    > "instead of waiting for the HTTP requests for these objects, the server 
    > can analyze the HTML page, identify the objects that are needed, and 
    > send them to the client before receiving explicit requests for these 
    > objects"

### HTTP/3

- QUIC: new 'transport' protocol implemented in teh application layer to wrap 
  the UDP protocol
- HTTP/3: designed to operate over QUIC, non-standardized, in Internet drafts
