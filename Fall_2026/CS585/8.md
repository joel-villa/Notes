## Cookies

- What cookies are good for:
    - Shopping cart status (ecommerce)
    - Session state 
    - Advertizing

### Example

- When you don't have cookies -> get default advertisement
- When you have cookies -> got a NYT cookie, that tracks us, and will always 
be referenced
    - When we run a request to the ad server, teh ad service has it's own 
cookie on us, so when the object is loading the ad server is getting an HTTP
get request
    - Ad has seperate cookie from the server (since it is an object being 
      loaded on the page)
    - Now we have two cookies, one from the server, and a third party cookie 
      from an advertiser you didn't choose to vise
- Third party cookies can populate information on you, get fed more info
- Once you try to access that object, all of its contents will load unless 
  you have blockers ahead of time

### DPR and Cookies

- Cookies can identify an individual, personal data, and you should have power 
  over how your data gets used


### Cookies vs. Fingerprinting

- Cookies get set on the device, you can change the way you're device saves 
  cookies
- Fingerprinting: get metadata on the device + connnection, you have a lot less 
  on whether or not you get fingerprinted.
- Delete your cookies -> treated as new user, could be fingerprinted 
- Light Mode vs. Dark Mode:
    - Can go with browser default akin to fingerprinting
    - Can save user's choice akin to a cookie

## DNS: Domain Name System

- hostname: user readable
- IP address: actual uniique identifier
- EX: Standford:
    - Standford kept a file with 400 addresses shared and stored on all end-
      devices
    - DNS made in 1980s as solutiion
- DNS implemented on teh application layer (kept at network's edge, not 
  part of the router's functionality)

### Services, Structure

= Why Decentralized?
    - Doesn't scale
    - EX: Akamai DNS has 2.2 trillion DNS queries per day

### A Distributed Hierarchical Database

- Root DNS at top
- .com, .org, .edu, below
- Can get authoratative information from the servers such as yahoo.com

### Root Name Servers

= Contact of last resort, want to access them the least ammount of times
- Gives basic internet functionality
- Governed by ICANN
- 300 servers in the US, 305 in Europe, copies of the information

### Top level Doain, and Authorative Servers

- Example: Educause governs all `.edu` domain names
- Why more domain signifiers than used to be:
    - EX: .cloud, .microsoft, etc.
- How often to update?

### DNS Records

- Format: name, value, type, time to live
- DNS is responsible for updating and keeping records
- Updates starts at the authorative server

### Local DNS  Name Servers

- Can get out of date information
- Each IP<S-Del>SP has local DNS server

### Name Resuolution: Iterated Query

- Start at the host, first talk to local DNS server
- "I don't know this name, but you should ask this server"

### Name Resolution: Recursive Query

- Ask each server to do the search for us, as opposed for us asking where to 
  next

### DNS Records

- Type=A, hostname -> IP address
- Type=NS, domain -> hostname
- Type-CNAME, alias -> canonical
- Type=MX, hostname -> SMTP mail server

## CDNs

### Context

- Video traffic is 60 to 80 percent of traffic
- Challenges: many devices, many connections, how to make connection reliable

### Multimedia: video

- To help video traffic -> compress videos in a smart way
- How to be smart about this transition without losing info about that frame
- Two Approaches to video compression:
    - Spatial: the next 40 entries are purple, this is the info we save
    - Temporal: save all of frame i, only save some amount of information that changes
    - Main idea: store the edges, where things change

### CDNs

- How to scale this?
    - Store multiple copies of a single video across multiple sites
    - Enter Deep: 
        - Want videos few hops away from the end-devices
        - Faster, but need more servers
    - Bring Home:
        - Have more hops to do, but less servers
        - Slower, but less severs

### Netflix

- Ask Netflix server's where to look for it, and get a response of what server 
  to use.

## Socket Programming

- Socket is the dooor, how we get info in and out the house 
- Reminder, all logical: end systems are not linked together, 
    - All these layers make it feel like they are talking to eachotehr

### Socket Programming with UDP

- UDP: no connection betwen client and server 
    - No hanshaking
    - Data loss + out of order data
    - 'Unreliable'

### Client/Server Socket Interatction: UDP

- Server creates socket attached to a port
- Client creates datagram to port, sends it to server
- Server replies using same socket, and then closes
- Server doesn't exist for the client to be able to run
- Silent failure

### Socket programming with TCP

- Create a socket with process + port number
- Server has its own socket -> can take on multiple clients
- One port per server, multiple ports per client
- 'Reliable': no data loss, in order data

### Client/Server Socket Interaction: TCP

- Server creates socekt, waits for incoming traffic
- client sends a message to particular socket
- server recieves/sends on same socket
- Connection closure on both sides
- In TCP: 
    - Client closes socket, server closes connection
### Q and A

- Socket is a programatically built thing
- 65k max number of sockets (determined by OS)


## Transport Layer Intro

### Overview

- Multiplexing + demultiplexing: encode and decode info
- Flow + congestion control: where to go if network is busy
- How do TCP and UDP work?

### Compairing layers

- App layer: 
    - entirely on end-systems
    - Talks to transport layer via socket
- Transport Layer:
    - Don't care about data, just how to move it (UDP or TCP)

### Transport Services and Protocols

- Why DNS in application layer? only humans care about hostname
- Logical communication: a server and a client talking to eachother via 
  transport layer as if there's nothing in between
- Packets:
    - Sender breaks message into segments, that reciever has to deal with

### Transport Layer Actions

- Multiplexing & demultiplexing: adding headers, vs removing headers and 
  keeping emssage
- Sender:
    - Ap passes message
    - Transport layer adds some header fields, 
- Receiver:
    - Remove the headers, and keep the message

### 2 Principal Internet Transport Protocols

- Transport layer doesn't have any guarantees on delay or bandwidth
